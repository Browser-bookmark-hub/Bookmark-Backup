# 当前变化增量刷新与全量兜底：当前实现归纳

日期：2026-07-15

## 定位

本文记录 `history.html` 中「当前变化」视图的实时刷新模型，重点说明：

- 书签 API 事件低频时如何走增量。
- DOM / 存储分别更新什么。
- 何时切换为完整 `getTree()` 快照和全量 diff。
- 简略、详细、集合三种视图如何从同一份变化数据派生。

当前事实来源仍以代码为准，主要位置：

- `Bookmark-Backup-main/history_html/history.js`
- `Bookmark-Backup-main/background.js`

## 监听的书签事件

「当前变化」前台页面监听 5 类书签 API：

- `bookmarks.onCreated`
- `bookmarks.onRemoved`
- `bookmarks.onChanged`
- `bookmarks.onMoved`
- `bookmarks.onChildrenReordered`

后台也监听这些结构/内容变化事件，并额外处理导入事件：

- `bookmarks.onImportBegan`
- `bookmarks.onImportEnded`

导入事件不放到前台逐事件处理。导入开始后由后台设置 `bookmarkImportingFlag` / `canvasMarkerBulkMode`，前台进入 mute；导入结束后后台延迟一次统一刷新，避免导入期间大量暴力重刷。

## 阈值以下：前台先增量维护缓存树

阈值以下且当前变化视图处于可实时处理的状态时，前台使用之前 `getTree()` / 后台快照拿到的 `cachedCurrentTree` 作为内存缓存。

监听到书签 API 事件后，相关增量函数会先检查当前 view、懒加载开关和 mute 状态；条件满足时，按事件里携带的信息直接修改这棵缓存树：

| 事件 | 使用的信息 | 前台缓存处理 |
| --- | --- | --- |
| `onCreated` | `id`、`bookmark.parentId`、`bookmark.index`、`title`、`url` | 在父节点 children 中插入新节点 |
| `onRemoved` | `id`、`removeInfo.parentId`、缓存索引 | 从父节点 children 中移除节点 |
| `onChanged` | `id`、`changeInfo.title`、`changeInfo.url` | 更新节点标题或 URL |
| `onMoved` | `id`、`moveInfo.oldParentId`、`moveInfo.parentId`、`moveInfo.index` | 从旧父级移除，插入新父级指定位置 |
| `onChildrenReordered` | `parentId`、`reorderInfo.childIds` | 按 `childIds` 重排父节点 children |

这一步是数据层增量，不是只改一个 DOM 节点的纯 DOM patch。

但要区分两件事：

- 这些事件处理函数在当前变化视图可实时处理时，会先增量维护 `cachedCurrentTree`，供预览路径、tooltip、懒加载提示等逻辑及时使用。
- 当前变化预览真正刷新时，现有代码仍会调用 `ensureChangesPreviewTreeDataLoaded()`，重新取得完整当前树快照并计算 `treeChangeMap`。

因此，当前实现不是“阈值以下完全依靠事件 delta 完成 diff”。更准确的模型是：事件层在条件满足时先增量维护缓存，渲染层做 DOM 局部刷新；不满足条件时先标记 stale，等用户切回当前变化视图或页面重新可见后再刷新。预览树数据通常仍重新同步完整快照并做整树 diff。

## DOM 层：局部重渲，不整页刷新

书签事件标记当前变化数据 stale 后，会尝试实时刷新：

- 当前页面必须已经初始化。
- 当前 view 必须是 `current-changes`。
- 页面必须可见。
- 当前没有导入/恢复/bulk mute。

满足条件时，`scheduleCurrentChangesRerender()` 做 350ms debounce，然后调用 `refreshCurrentChangesViewInPlace()`。

`refreshCurrentChangesViewInPlace()` 做的是局部刷新：

- 更新当前变化操作摘要（新增/删除/移动/修改）。
- 重新渲染「当前变化」预览树容器。
- 重建当前变化搜索索引。

正常路径不会重刷整个 `history.html` 页面。不过存在两类回退：尚未渲染出摘要/diff 容器，或者变化从有变无时，会调用 `renderCurrentChangesViewWithRetry()` 重新渲染整个「当前变化」视图区域。

如果当前不在「当前变化」视图，或者页面不可见，则只设置 `currentChangesNeedsRefreshOnNextOpen`。用户切回「当前变化」或页面重新可见时再刷新。

## 前台 add/remove 批处理阈值

前台对 `onCreated` / `onRemoved` 有单独的批处理保护：

- `BULK_ADD_REMOVE_QUIET_MS = 220`
- `BULK_ADD_REMOVE_THRESHOLD = 300`

流程：

1. `onCreated` / `onRemoved` 先入 `pendingAddRemoveEvents` 队列。
2. 220ms 内没有新的 add/remove 后 flush。
3. 如果本批数量 `< 300`，且当前变化视图允许实时处理，逐条应用增量到 `cachedCurrentTree`。
4. 如果本批数量 `>= 300`，放弃逐条增量，标记 stale；在当前变化视图可刷新时安排完整当前树快照刷新，否则等下次打开/可见时补刷新。

`onChanged`、`onMoved`、`onChildrenReordered` 不走这个 300 条前台队列；它们直接尝试增量应用，再走 350ms 的当前变化局部刷新 debounce。

这里的 `300` 只控制“是否逐条修改前台缓存树”，不是“是否执行完整快照/diff”的总开关。即使本批 `< 300`，后续当前变化预览刷新仍通常会重新取得完整快照并计算 `treeChangeMap`。

## 后台全局 bulk 阈值

后台有全局大量变化防护：

- `BOOKMARK_BULK_WINDOW_MS = 1500`
- `BOOKMARK_BULK_THRESHOLD = 30`
- `BOOKMARK_BULK_QUIET_MS = 1200`

含义：

1. 1500ms 内累计 30 个书签事件后，进入 bulk mode。
2. 后台设置 `bookmarkBulkChangeFlag` 和 `canvasMarkerBulkMode`。
3. 前台 `history.html` 任意 view 都会感知 mute 状态，暂停昂贵刷新。
4. 安静 1200ms 后退出 bulk。
5. 后台统一触发一次 `handleBookmarkChange()`，前台按当前 view 做一次补刷新。

这和前台 `300` 条 add/remove 阈值不是一回事：

- `30 / 1500ms` 是后台全局防护，覆盖正常进入 `handleBookmarkChange()` 的书签结构/内容事件；导入和恢复期间会走独立 mute/延迟刷新路径，不纳入这个计数口径。
- `300` 是当前变化前台 add/remove 队列的“增量转全量”阈值。

## 存储层增量缓存

后台维护当前变化缓存：

- `CURRENT_CHANGES_CACHE_KEY = 'current-changes-cache:v3'`

小变化时，后台会把事件转成 delta，尝试增量更新存储里的当前变化数据：

- `created`
- `removed`
- `moved`
- `changed`

这条增量更新只在已有 `current-changes-cache:v3` payload/meta 且当前没有导入、恢复、bulk 或恢复事件宽限期时成立；否则会跳过 delta 或回到完整计算路径。前台 `getDetailedChanges(false)` 会优先读取这个缓存。缓存的有效性依赖：

- `lastBookmarkData.timestamp`
- `lastBookmarkChangeTime`

如果缓存 meta 与当前基线/最后变化时间一致，则直接使用缓存数据；否则回到完整计算路径。

`onChildrenReordered` 不适合做精确存储 delta，因为它只提供父级和重排后的 `childIds`，没有单个主动移动节点的完整语义。因此它主要用于标脏、刷新当前树快照和让 diff 重新计算。

## 完整快照与净差异计算

当前变化预览的数据准备主路径本身就会调用 `ensureChangesPreviewTreeDataLoaded()`：

1. `getBookmarkTreeSnapshot()` 获取当前树。
   - 优先请求后台 `getBookmarkSnapshot`。
   - 后台快照未 stale 时可以直接返回内存/会话快照。
   - 后台快照 stale 时，`BookmarkSnapshotCache.ensureFresh()` 先考虑导入/恢复期间已有树和 session cache；这些都不可用时才回到 `bookmarks.getTree()`。
2. 从 `lastBookmarkData.bookmarkTree` 获取上次备份树，作为 old tree。
3. `detectTreeChangesFast(oldTree, currentTree)` 计算 `treeChangeMap`。
4. 如果存在删除节点，用 `rebuildTreeWithDeleted(oldTree, currentTree, treeChangeMap)` 把 deleted 节点合回展示树。
5. 渲染当前变化摘要、预览树、搜索索引。

下面这些情况会额外明确要求或更容易触发完整快照刷新/重新渲染：

- 页面首次打开当前变化，没有可用 `cachedCurrentTree`。
- 当前变化缓存失效，或者后台书签事件已把 `BookmarkSnapshotCache` 标记为 stale。
- 前台 add/remove 批量达到 `>= 300`。
- 增量应用失败，例如父节点不在缓存索引里。
- `onChildrenReordered` 的 `childIds` 与缓存 children 对不上。
- 导入、恢复、大量变化 bulk 结束后的统一刷新。
- 三种模式导出需要重新准备完整树和 `changeMap`。

因此，增量事件目前主要用于及时维护前台缓存状态，并避免逐事件重建整个当前变化 DOM；它们并没有替代预览刷新阶段的完整树同步和整树 diff。三种视图最终都基于“当前完整树 vs 上次备份树”的净差异。

## 简略 / 详细 / 集合视图

当前变化实时视图的三种模式不是从“详细 DOM”派生。

它们共用同一份底层数据：

- `cachedOldTree`
- `cachedCurrentTree`
- `treeChangeMap`
- `treeToRender`
- `normalizedStats`

`resolveCurrentChangesRenderState()` 会准备这些数据。

三种模式的差异只在最终渲染形态：

| 模式 | 数据来源 | 渲染语义 |
| --- | --- | --- |
| 简略 | `treeToRender + treeChangeMap` | 保留原生书签树层级，但过滤无变化分支，只显示变化路径 |
| 详细 | `treeToRender + treeChangeMap` | 显示完整上下文，变化节点打标，展开状态影响可见范围 |
| 集合 | `treeToRender + treeChangeMap + stats` | 按新增、删除、移动、修改重新分桶为集合树 |

集合模式通过 `buildCurrentChangesExportTreeManual(..., { mode: 'collection' })` 从实时树和 `changeMap` 生成，不依赖详细 DOM。

注意：历史记录详情里如果已经持久化了 `detailedChildren`，会存在从 detailed children 派生简略/集合的路径：

- `deriveSimpleChildrenFromDetailed(detailedChildren)`
- `deriveCollectionChildrenFromDetailed(detailedChildren, stats, lang)`

这是历史记录持久化数据的兼容/导出路径，不是当前变化实时预览的主路径。

## 一句话总结

小变化时：当前变化视图可实时处理时，前台先增量修改 `cachedCurrentTree`；后台在已有有效缓存且未处于导入/恢复/bulk 等状态时，尝试增量更新 `current-changes-cache:v3`。UI 正常路径只局部刷新当前变化区域；但预览树数据刷新仍通常会取得完整当前树并重算 `treeChangeMap`。

大变化或前台缓存不可信时：停止逐条修改前台缓存，标记 stale，并在当前变化视图可刷新时安排完整快照刷新；不在当前变化视图或页面不可见时，等下次打开/可见时补刷新。无论小变化还是大变化，三种预览模式最终都以完整当前树和上次备份树的净差异为准。
