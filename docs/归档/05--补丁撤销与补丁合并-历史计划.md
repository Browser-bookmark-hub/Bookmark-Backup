# 补丁撤销/补丁恢复：当前实现审计

日期：2026-07-16

## 结论

`565209e5889dba60b7b33d95c8642982d1d6d6e4` 是文档 commit，只新增/更新归档文档，没有改运行时代码。因此这里按当前 `HEAD` 的代码现状判断。

结论分两层：

- 补丁撤销：当前实现基本符合“按 ID 执行新增/删除/移动/修改”的目标。
- 补丁恢复：在备份历史页里，补丁恢复预览和补丁撤销预览一样，都是拿当前 Chrome 书签树与目标快照按 ID 体系做 diff；在稳定 Bookmark ID 来源上，当前实现也会执行新增、删除、移动、修改。但不能把所有恢复入口都笼统说成“补丁恢复已经完全正确”。popup 主 UI / 外部恢复来源的预检链路会对目标树补 ID、root remap、`normalizeTreeIds()`，而实际执行链路没有把这棵归一化后的目标树传入 patch 执行。也就是说，某些无稳定 ID 或 ID 大幅变化的来源，预览/决策看到的身份映射和真正执行的身份映射可能不是同一份事实。

## 事实证据

### 1. 后台补丁执行确实支持四类操作

实际 patch 执行入口是 `executePatchBookmarkRevert(snapshotTree, options)`，位置：`Bookmark-Backup-main/background.js:24046`。

当前执行计数包含四类：`removed`、`created`、`moved`、`updated`，见 `Bookmark-Backup-main/background.js:24063` 到 `Bookmark-Backup-main/background.js:24066`。

执行阶段如下：

- 新增：目标快照有、当前没有时创建节点；创建书签/文件夹并 `created += 1`，见 `Bookmark-Backup-main/background.js:24083` 到 `Bookmark-Backup-main/background.js:24117`。
- 修改：同 ID 节点标题或 URL 不一致时调用 `browserAPI.bookmarks.update()`，并 `updated += 1`，见 `Bookmark-Backup-main/background.js:24145` 到 `Bookmark-Backup-main/background.js:24192`。
- 跨父级移动：父级不同则进入 `moveQueue`，调用 `browserAPI.bookmarks.move(id, { parentId })`，并 `moved += 1`，见 `Bookmark-Backup-main/background.js:24198` 到 `Bookmark-Backup-main/background.js:24242`。
- 删除：目标树没有的当前节点会进入 `deleteRoots`，文件夹用 `removeTree()`，书签用 `remove()`，并 `removed += 1`，见 `Bookmark-Backup-main/background.js:24244` 到 `Bookmark-Backup-main/background.js:24288`。
- 同级排序：对同父级 children 做 scan-and-align，调用 `browserAPI.bookmarks.move(targetChromeId, { parentId, index })`，并 `moved += 1`，见 `Bookmark-Backup-main/background.js:24290` 到 `Bookmark-Backup-main/background.js:24354`。

函数最后返回 `{ created, removed, moved, updated }`，见 `Bookmark-Backup-main/background.js:24371`。所以旧说法里如果暗示“补丁恢复只新增/删除”，已经不符合当前代码。

### 2. 补丁恢复实际走同一个 patch 执行函数

popup 恢复执行路径中，如果最终策略是 `patch`，后台调用 `executePatchBookmarkWithAutoRollback(tree, ...)`，见 `Bookmark-Backup-main/background.js:35388` 到 `Bookmark-Backup-main/background.js:35395`。

`executePatchBookmarkWithAutoRollback()` 内部直接调用 `executePatchBookmarkRevert(snapshotTree, ...)`，见 `Bookmark-Backup-main/background.js:24390` 到 `Bookmark-Backup-main/background.js:24404`。

这说明“补丁恢复”和“补丁撤销”的底层 patch 执行能力是同一套，所以稳定 ID 条件下补丁恢复也具备移动/修改执行能力。

### 3. 备份历史页补丁恢复预览也是 ID diff

备份历史页的恢复预演在 `buildRestoreDiffSummary(record, strategy, options)` 中先取当前 Chrome 书签树，再把 `record.bookmarkTree` 作为目标树，见 `Bookmark-Backup-main/history_html/history.js:12775` 到 `Bookmark-Backup-main/history_html/history.js:12784`。

当不是导入合并时，策略决策先用 `computeIdStrictPatchChangeMap(currentTree, targetTree)` 做严格 ID diff，见 `Bookmark-Backup-main/history_html/history.js:12789` 到 `Bookmark-Backup-main/history_html/history.js:12798`。

展示用的 `rawChangeMap` 优先走 `detectTreeChangesFast(currentTree, targetTree, { useGlobalExplicitMovedIds: false })`，失败才回退到 `computeIdStrictPatchChangeMap()`，见 `Bookmark-Backup-main/history_html/history.js:12799` 到 `Bookmark-Backup-main/history_html/history.js:12809`。这里仍是当前树 vs 目标树的 ID 体系 diff，只是展示口径会用视觉移动算法处理同级排序。

真正进入预览页时，`switchToRestorePreview()` 直接使用传入的 `changeMap`；如果没有 map，才重新 `detectTreeChangesFast(currentTree, targetTree, ...)`，见 `Bookmark-Backup-main/history_html/history.js:13084` 到 `Bookmark-Backup-main/history_html/history.js:13106`。

补丁撤销预览同样是 `computeIdStrictPatchChangeMap(currentTree, targetTree)`，见 `Bookmark-Backup-main/history_html/history.js:4504` 到 `Bookmark-Backup-main/history_html/history.js:4507`，以及预览页兜底的 `Bookmark-Backup-main/history_html/history.js:4644` 到 `Bookmark-Backup-main/history_html/history.js:4648`。

所以，备份历史页里的“补丁恢复预览”和“补丁撤销预览”确实是一类：都是找出“当前 Chrome 书签树 -> 目标快照树”的 ID 差异。区别不在算法类型，而在目标快照来源：补丁撤销的目标是撤回去的基线；补丁恢复的目标是用户选中的历史版本。

### 4. popup 主 UI 预检链路会做目标树归一化

popup 的补丁/覆盖/自动恢复预检会发 `buildOverwriteRestorePreview`，后台入口在 `Bookmark-Backup-main/background.js:35519`。

这条预览链路会：

- 复制目标树，见 `Bookmark-Backup-main/background.js:35549` 到 `Bookmark-Backup-main/background.js:35552`。
- 补缺失 ID，见 `Bookmark-Backup-main/background.js:35554`。
- 做顶层 root ID remap，见 `Bookmark-Backup-main/background.js:35556` 到 `Bookmark-Backup-main/background.js:35558`。
- 调用 `normalizeTreeIds(targetTree, currentTree, { referenceRootIds, strictGlobalUrlMatch: true })`，见 `Bookmark-Backup-main/background.js:35560` 到 `Bookmark-Backup-main/background.js:35565`。
- 用归一化后的 `targetTree` 计算 patch 决策摘要和视觉变化，见 `Bookmark-Backup-main/background.js:35575` 到 `Bookmark-Backup-main/background.js:35597`。

`normalizeTreeIds()` 的匹配事实：

- 缺 ID 会补 `__restore_tmp_N`，见 `Bookmark-Backup-main/background.js:33041` 到 `Bookmark-Backup-main/background.js:33072`。
- 先做原 ID 精确匹配，见 `Bookmark-Backup-main/background.js:33218` 到 `Bookmark-Backup-main/background.js:33239`。
- `normalizeTreeIds()` 支持手动匹配，见 `Bookmark-Backup-main/background.js:33241` 到 `Bookmark-Backup-main/background.js:33300`；但当前 `buildOverwriteRestorePreview()` 主链路没有传入 `manualMatches`，实际 patch 执行前也不会用手动匹配结果归一化目标树。
- 支持父子结构匹配，见 `Bookmark-Backup-main/background.js:33303` 到 `Bookmark-Backup-main/background.js:33363`。
- 支持全局 URL 匹配，且 `strictGlobalUrlMatch` 为 true 时不会在多候选里随便取第一个，见 `Bookmark-Backup-main/background.js:33365` 到 `Bookmark-Backup-main/background.js:33436`。
- 文件夹走全局标题匹配，多候选会记录歧义，见 `Bookmark-Backup-main/background.js:33438` 到 `Bookmark-Backup-main/background.js:33508`。

因此，预览层确实有“无稳定 ID 快照尽量映射到当前 ID”的能力。

### 5. 但 popup 实际执行没有复用预检归一化后的目标树

实际恢复入口先提取原始 `tree`，见 `Bookmark-Backup-main/background.js:35039` 到 `Bookmark-Backup-main/background.js:35048`。

后续执行 patch 时传入的仍是这个 `tree`，见 `Bookmark-Backup-main/background.js:35388` 到 `Bookmark-Backup-main/background.js:35395`。从当前文件搜索结果看，`normalizeTreeIds()` 只出现在结构可比快照/预览类路径和 `buildOverwriteRestorePreview()` 中；没有出现在 `restoreSelectedVersion` 的实际 patch 执行前。

popup 传给执行层的 `preflight` 也只包含身份字段、策略、分数和 `precomputedDiffSummary`，不包含归一化后的 `targetTree` 或 ID 映射，见 `Bookmark-Backup-main/popup.js:17528` 到 `Bookmark-Backup-main/popup.js:17598`，以及执行时把 `preflight` 放入 `restorePayload` 的 `Bookmark-Backup-main/popup.js:17805` 到 `Bookmark-Backup-main/popup.js:17819`。

所以必须把补丁恢复的正确性限定为：实际 patch 执行依赖目标快照自身的 ID 与当前浏览器树可比。预览中靠 `normalizeTreeIds()` 识别出来的映射，目前不是执行层的输入。

### 6. 不稳定来源会被禁用或转覆盖，但范围较粗

当前不适合稳定 ID patch 的来源只明确排除了 `html` 和 `changes_artifact`，见 `Bookmark-Backup-main/background.js:23900` 到 `Bookmark-Backup-main/background.js:23906`。

执行恢复时，如果用户手选 patch 且来源不稳定，直接返回“补丁恢复不可用”，见 `Bookmark-Backup-main/background.js:35243` 到 `Bookmark-Backup-main/background.js:35254`。

预览/预检时，如果 auto 遇到不稳定来源，会把策略改成 overwrite，见 `Bookmark-Backup-main/background.js:35582` 到 `Bookmark-Backup-main/background.js:35591`。

popup 端也会在 patch 预检发现 `patchUnsupported` 或 ID churn 过大时禁用确认按钮，见 `Bookmark-Backup-main/popup.js:16856` 到 `Bookmark-Backup-main/popup.js:16860`，以及提示和禁用按钮的 `Bookmark-Backup-main/popup.js:17375` 到 `Bookmark-Backup-main/popup.js:17400`。

这个保护是存在的，但它不是“执行层使用预览归一化 ID 映射”的等价替代。

### 7. UI 文案和完成提示已经包含移动/修改

history 页补丁撤销说明写明执行层支持新增/删除/移动/修改，见 `Bookmark-Backup-main/history_html/history_i18n.js:573` 到 `Bookmark-Backup-main/history_html/history_i18n.js:579`。

history 页补丁撤销预览摘要会显示新增、删除、移动、修改，见 `Bookmark-Backup-main/history_html/history.js:4519` 到 `Bookmark-Backup-main/history_html/history.js:4544`。

popup 补丁恢复确认说明写明“ID 匹配执行新增/删除/移动/修改”，见 `Bookmark-Backup-main/popup.js:16785` 到 `Bookmark-Backup-main/popup.js:16790`。

popup 补丁恢复预览摘要在 patch 模式下会显示新增、删除、移动、修改，见 `Bookmark-Backup-main/popup.js:17249` 到 `Bookmark-Backup-main/popup.js:17263`。

popup 补丁恢复完成提示也显示新增、删除、移动、修改，见 `Bookmark-Backup-main/popup.js:17899` 到 `Bookmark-Backup-main/popup.js:17908`。

### 8. “补丁后校验”不是强校验

恢复完成后会调用 `runRestoreRecoveryPostApplyVerification()`，见 `Bookmark-Backup-main/background.js:35428` 到 `Bookmark-Backup-main/background.js:35439`。

但该函数当前直接跳过重型结构校验，返回 `{ success: true, verifyPassed: true, verifyMode: 'none' }`，见 `Bookmark-Backup-main/background.js:23829` 到 `Bookmark-Backup-main/background.js:23835`。

所以不能在文档里写成“补丁后已有结构强校验保证结果正确”。当前事实只能说：执行后会进入恢复事务收尾和基线提交，但结构校验被显式跳过。

## 当前判断

补丁撤销：对。它是严格按当前树和目标快照的 ID 差异执行，并且代码实际覆盖新增、修改、移动、删除、同级排序。

补丁恢复：分入口看。备份历史页里的补丁恢复预览和补丁撤销预览是一类 ID diff；对稳定 ID 的历史快照、版本快照，当前底层执行能力是对的，它不是只新增/删除。但 popup 主 UI / 外部恢复来源里，如果只能靠启发式 `normalizeTreeIds()` 才能识别“同一节点”，当前实现还不能宣称 patch 执行一定按预检里的映射恢复。popup 预检归一化和执行输入没有完全闭环。

## 建议更新后的目标

如果要把“补丁恢复对吗”推进到可确认状态，需要补齐下面任一条：

1. 执行层复用预检生成的归一化 `targetTree` 或明确的 ID 映射，并在执行前校验 preflight 与当前树仍兼容。
2. 或者收紧策略：凡是需要 `normalizeTreeIds()` 才能匹配的来源，一律只允许 overwrite/auto->overwrite，不允许 patch。
3. 恢复后重新启用实际结构校验，至少比较执行后当前树与目标树的结构/标题/URL/顺序，而不是 `verifyMode: 'none'`。

在这些补齐之前，文档应避免写“补丁恢复已经完全正确”。更准确的表述是：

> 当前补丁恢复执行层已支持新增、删除、移动、修改；备份历史页的补丁恢复预览与补丁撤销预览同属当前 Chrome 树 vs 目标快照树的 ID diff。稳定 ID 来源下可按 patch 语义恢复。popup 主 UI / 外部来源的无稳定 ID 或 ID churn 场景仍存在预检归一化与执行输入不一致的边界，不能把这类预检结论直接等同于执行正确性。
