# 五种恢复与导入操作及 `folderType` 根边界

状态：2026-07-28 当前实现快照与维护规范。归档文档不替代当前代码；恢复、撤销或根识别逻辑变更后必须重新核对 `Bookmark-Backup-main/`。

## 1. 范围

本篇统一记录书签备份项目中五种用户可见操作：

1. HTML 页面：补丁撤销
2. HTML 页面：补丁恢复
3. HTML 页面：覆盖撤销
4. HTML 页面：覆盖恢复
5. 主 UI 恢复二级界面的本地恢复（导入合并或覆盖恢复）

主 UI 恢复二级界面的覆盖恢复与 HTML 页面覆盖恢复共用同一套背景恢复模型；导入合并则使用独立的“新增导入文件夹”模型。主 UI 的本地“选择文件”与“选择文件夹”是恢复来源入口，不是额外的第六种写入语义：实际采用覆盖还是合并，必须在选中条目、读出真实树后再次判定。

## 2. 根身份事实

- 浏览器树来自 `chrome.bookmarks.getTree()`。
- 顶层根优先使用 API 返回的 `folderType`，并在增强 HTML 快照中同时记录 `syncing`；项目生成的 JSON 快照保留原始根节点字段。
- 根匹配优先级为：
  1. `folderType + syncing`
  2. `folderType`
  3. 旧 ID、标题和历史兼容 key
- `folderType` 是英文内部枚举，不随界面语言变化。`title` 与旧 ID 只能服务于受控旧项目快照的有限兼容，不能证明第三方标准 HTML 的顶层目录就是浏览器根。
- 根 ID 只属于当前浏览器配置文件，远端快照中的 Chrome ID 不能直接作为目标 `parentId`。
- 快照原则上保留 API 返回的完整书签树，当前实现没有像 Bookmark Canvas 那样对未知根做永久同步白名单过滤。

HTML 增强快照通过 `bookmarkBackupMeta.rootDescriptors` 保存顶层根的 `title`、`folderType` 和 `syncing`。项目 JSON 和带完整根元数据的增强 HTML 可以进入覆盖根计划；当重复根缺少 `syncing` 时，覆盖恢复应保守失败，不猜测。

第三方原生 Netscape HTML 不携带项目根身份。对于主 UI 的本地来源，只要解析出的任一顶层根缺少 `folderType`，该 HTML 就只能导入合并，不能覆盖恢复。此规则与中文、英文、其他语言、浏览器品牌、用户改名和根 ID 无关：不能靠扩展标题对照表或 `1/2/3` 一类 ID 猜测来放开高危覆盖。

## 3. 五种操作总览

| 操作 | 目标状态 | 根处理 | 实际写操作 | 受限根结果 |
| --- | --- | --- | --- | --- |
| HTML 补丁撤销 | 回到最近一次备份状态 | 只映射三类用户根；保护其他根的整棵子树 | 对用户根内子项做新增、修改、移动、删除、排序 | `managed`、Workspace、未知根不参与写操作 |
| HTML 补丁恢复 | 回到选定历史快照 | 同上，目标是选定历史快照 | 同上 | 同上 |
| HTML 覆盖撤销 | 用最近一次备份覆盖已匹配的用户根 | 只为三类用户根生成根计划 | 只清空已匹配用户根，再递归创建快照内容 | 其他根保持不变；删除失败按严格模式失败 |
| HTML 覆盖恢复 | 用选定历史快照覆盖已匹配的用户根 | 同上 | 同上 | 同上 |
| 主 UI 本地恢复 | 项目快照可覆盖；普通 HTML 只追加导入 | 覆盖须有完整源根身份；合并只验证目标父目录位于三类用户根下 | 覆盖时按根计划重建；合并时在目标根下新建导入文件夹并复制源数据 | 缺少 `folderType` 的本地 HTML 强制转为合并；不按源标题/ID 写回浏览器根 |

## 4. HTML 页面：补丁撤销

入口是历史页当前变化/撤销界面的 `executeRevert()`，向后台发送 `revertAllToLastBackup`。后台根据预演结果执行 `executePatchBookmarkRevert()`，目标是最近一次备份树，而不是用户重新选择的历史记录。

执行顺序：

1. 读取当前树和目标快照。
2. 使用根匹配 key 把快照中的顶层根 ID 映射为当前浏览器根 ID。
3. 将根节点和顶层根容器加入 `protectedIds`；`managed`、Workspace 和未知根的整个子树都受保护。
4. 对普通节点执行：补建、标题/URL 更新、跨父级移动、删除多余节点、同级排序。

这不是根重建。它尽量复用当前节点和 ID，只修复差异。

根过滤边界：只有 `bookmarks-bar`、`other`、`mobile` 进入补丁目标树；显式非白名单 `folderType`、无法识别的根和旧快照中的未知根都会被跳过。

## 5. HTML 页面：补丁恢复

入口是历史页选中历史记录后的 `executeRestore()`，后台动作是 `restoreToHistoryRecord`，目标是选中的历史快照。执行算法与补丁撤销相同，区别只在目标快照来源：

- 补丁撤销：最近一次备份。
- 补丁恢复：选中的历史记录。

如果来源没有稳定 Bookmark ID，或预演检测到大范围 ID 变化，补丁恢复会被禁用；自动模式会选择覆盖恢复，手动补丁模式则返回不可用提示。

## 6. HTML 页面：覆盖撤销

入口仍是 `executeRevert()`，但预演选择 `overwrite` 后，后台使用 `restoreSnapshotTree()` 将当前树恢复到最近一次备份。

覆盖流程不是修改根节点，而是：

```text
读取当前 getTree()
  -> 按 folderType + syncing / folderType / 旧 key 建立根映射
  -> 清空当前根容器的子项
  -> 在映射后的真实根 ID 下递归 create()
  -> 更新基线并做恢复后校验
```

当前恢复白名单只允许 `bookmarks-bar`、`other`、`mobile`。因此：

- `managed`、Workspace 和其他未知根不进入清空列表，也不进入恢复 assignment。
- 覆盖只清空快照中实际匹配到的白名单用户根；快照缺少的根和非白名单根保持不变。
- 清空阶段使用严格删除；删除或重建失败会中止并返回失败，不把部分结果当作成功。

覆盖失败会返回 `success: false`，记录恢复事务失败并保留安全快照/恢复事务供后续处理；不能把浏览器拒绝写入解释为成功。发生部分写入时，不应假设已经自动恢复到操作前状态。

## 7. HTML 页面：覆盖恢复

入口是历史页选定快照后的 `executeRestore()`，或主 UI 恢复二级界面的覆盖策略；两者最终都使用同一类根计划和覆盖执行模型，区别只是快照来源和 UI 入口。主 UI 的本地标准 HTML 在真正读取书签树后会被降级为导入合并，不会进入这条覆盖路径。

根识别与覆盖撤销完全相同，区别是目标：

- 覆盖撤销：最近一次备份。
- 覆盖恢复：用户选中的历史快照、HTML 文件或 JSON 快照。

覆盖恢复遇到根缺失、根身份歧义或快照没有足够的 `syncing` 信息时，会在写入前返回根计划失败。若根已经映射成功，之后的清空/重建仍受浏览器实际写权限约束。

## 8. 主 UI：导入合并

导入合并不执行“按 `folderType` 找到原根后覆盖”。它的语义是浏览器式导入：

1. 读取当前书签根。
2. 使用用户指定的 `importParentId`，否则默认选择 `other`、书签栏或第一个可用根。
3. 在目标父文件夹下创建一个新的导入文件夹。
4. 把源快照的顶层根作为普通子文件夹复制进去。
5. 递归创建书签和子文件夹，不删除当前已有内容。

因此源快照中的 `bookmarks-bar`、`other`、`mobile`、`managed`、Workspace 或未知根都不会被当作目标浏览器根去写回；它们只会作为新导入文件夹下面的普通数据副本。

显式 `importParentId` 必须位于三类用户根的子树内；指向 `managed`、Workspace 或未知根会在创建导入文件夹前失败。导入创建阶段若浏览器拒绝写入，会返回失败并保留恢复事务信息。

### 8.1 本地 HTML 的二次检查与降级

主 UI 的恢复列表第一层只能看到文件名、目录索引或轻量元数据，不能据此安全决定覆盖。因此单文件和文件夹选择都遵循同一条二次检查链：

```text
选择本地条目并点击覆盖恢复
  -> 读取实际 HTML / 书签树
  -> 覆盖预演检查每个顶层根的 folderType
  -> 任一根缺失 folderType：返回 requiresMerge
  -> UI 切换为导入合并并展示原因
  -> 执行前后台再次执行同一检查
```

后台使用 `getLocalHtmlMergeOnlyDecision()` 及 `restore_local_html_merge_only` 表达这一结果；`buildOverwriteRestorePreview()` 负责预演阶段返回 `requiresMerge`，`restoreSelectedVersion()` 在真正写入前重复拦截。因而 UI 的“覆盖恢复”选择只是预先意图，不能绕过实际数据校验。

该限制只针对本地、标准 HTML 缺少项目根身份的情形。项目导出的 JSON，以及解析后每个顶层根都有 `folderType` 的增强 HTML，仍可按正常覆盖流程处理；导入合并始终可预览和执行，因为它不把源顶层目录映射为目标浏览器根。

### 8.2 当前导入合并预览口径

主 UI 与 HTML 页面共用以下展示语义：

- 合并摘要展示为“添加后：书签 当前数 `+`导入数，文件夹 当前数 `+`导入数”。标签和当前数使用主题主文字色，只有导入增量为绿色。
- 预览树会显示实际导入目标路径。自动目标会读取当前浏览器真实根名称，按实际执行顺序优先其他书签、其次书签栏；不再显示“导入位置 /”这类人工前缀。
- 新建的导入结果文件夹以绿色文件夹图标、绿色名称和右侧绿色 `+` 标识呈现。重复的树内“导入合并预览”标题被隐藏；整版本预览的弹窗标题统一为“导入合并预览”。

## 9. `managed`、Workspace 与未知根的最终判断

### `managed`

`managed` 是管理员/受监管账号策略根。扩展通常可以读取，但不能通过 Bookmark API 创建、修改、移动或删除策略内容，也不能在另一台浏览器凭快照创建该根。

当前 Bookmark-Backup 的处理并不完全安全：

- 全量备份会保存它。
- 补丁和覆盖恢复都会跳过它及其后代；导入合并只把它作为普通源数据复制到可写目标下。

### Workspace 与未知根

当前代码没有统一的未知根隔离白名单：

- 全量备份会保存它们。
- `folderType` 只要有值，就可进入根匹配 key。
- 补丁和覆盖恢复都会跳过它们；导入合并只复制为普通源数据，不会映射或写入目标同名根。

这与 Bookmark Canvas 的“未知根本机隔离”策略不同，也是覆盖恢复优先级高于补丁优化的原因。

## 10. 失败、成功与回滚口径

- 根映射失败或存在不可消除的歧义：在写入前失败，返回 `success: false`；非白名单根则按策略跳过。
- 补丁写 API 失败：通常抛错，补丁操作失败；自动模式才允许回退覆盖。
- 覆盖清空阶段使用严格删除；删除失败中止恢复。
- 覆盖重建阶段或导入创建阶段失败：返回失败；已写入部分由恢复事务记录，不能假设自动回滚。
- 恢复事务和安全快照用于记录、验证和后续继续/回滚；不能把事务存在本身理解为每次失败都会自动无条件恢复原树。

## 11. 当前代码入口

- HTML 撤销入口：`Bookmark-Backup-main/history_html/history.js` 的 `executeRevert()`。
- HTML 恢复入口：`Bookmark-Backup-main/history_html/history.js` 的 `executeRestore()`。
- 主 UI 恢复入口：`Bookmark-Backup-main/popup.js`，后台统一进入 `restoreSelectedVersion()`。
- 本地 HTML 合并专用判定：`getLocalHtmlMergeOnlyDecision()`、`buildLocalHtmlMergeOnlyResponse()` 与 `buildOverwriteRestorePreview()`。
- 补丁执行：`background.js` 的 `executePatchBookmarkRevert()`。
- 覆盖计划与执行：`buildOverwriteRestorePlan()`、`restoreSnapshotTree()`、`executeOverwriteBookmarkRestore()`。
- 导入合并：`executeMergeBookmarkRestore()`。
- 根匹配：`getRootMatchKeys()`、`setRootMatchMapEntry()`、`getRootMatchMapValue()`。
- 受限根清空判断：`isWritableRootContainer()`。

## 12. 维护结论

补丁恢复/撤销只对三类白名单用户根执行局部节点差异操作；`managed`、Workspace 和未知根的整棵子树在计划、清空、创建、移动、删除和校验各阶段统一跳过。覆盖撤销/覆盖恢复只清空实际匹配的白名单用户根。

导入合并的目标是追加数据，不是恢复原根；目标父文件夹必须位于白名单用户根下，而完整快照和变化视图均作为普通数据复制到新建导入文件夹中。对主 UI 的本地第三方标准 HTML，缺少 `folderType` 就是只能合并的充分条件，不接受标题、语言、品牌或旧 ID 作为覆盖恢复依据；预演和执行都必须重复验证。
